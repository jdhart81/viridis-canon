# Publication binding design — REPORT_ONLY, not installed

The Comparator certificate proves exact formal inputs and binds a sealed manuscript. A later final manuscript can contain updated certification-status wording. That final manuscript needs its own reviewed binding before publication. `PUBLICATION_BINDING.json` records this transition; it does not issue or amend a Lean certificate, establish empirical validity, approve a DOI transaction, or act as a second verifier.

Order: unchanged Comparator/issuer certification → final manuscript → structure-aware diff → independent exact-hash review → approved review hash in corpus ledger → publication-binding receipt → existing claim/fidelity/publication gates → separately authorized publisher. No production publisher wiring changes are part of this work.

Required fields: standard `VRS-PUBLICATION-BINDING-1`; `status:PUBLICATION_BOUND`; SHA256/path of the unchanged certificate; original sealed PDF/TeX paths and hashes; exactly one final PDF and one final TeX and their hashes; SHA256 of the canonical classified diff; `diff_classification:VERIFICATION_STATUS_ONLY`; immutable review path/hash, certificate issuance time, independent review time and receipt issuance time (in that order, no future timestamps). A receipt is tied to the current final PDF/TeX bytes, not just a Run number or title. Byte-identical final manuscripts still require a reviewed receipt.

The independent review records `status:APPROVED_PUBLICATION_BINDING`, `scope:VERIFICATION_STATUS_TEXT_ONLY`, `pdf_correspondence_reviewed:true`, reviewer identity/time, the same certificate/final-manuscript/diff hashes. An entity's `approved_publication_binding_reviews` list in the authoritative corpus ledger must explicitly approve the review SHA256. This is a separate trust input: a self-authored receipt or `reviewed:true` cannot grant approval. The preparation tool writes DRAFT_AWAITING_INDEPENDENT_REVIEW only; this task approves no reviewer hash and issues no PUBLICATION_BOUND receipt. The approval writer/provider authorization must be settled during pipeline integration, after Justin reviews this design.

The consumer first reuses the existing hash-bound Comparator certificate assessment and source/mirror parity. It then recomputes the final file hashes and classified diff, checks the receipt and ledger-approved independent review, and still requires the existing complete claim-to-theorem/fidelity/disclaimer gate. Any absent/unreadable/tampered input, unauthorized reviewer hash, changed equation/theorem/numeric data, or non-status scientific prose is HOLD/CONJECTURE. Valid proof status remains separate from publication binding.

Allowed text changes are only explicit verification/certification status sentences and section titles. The classifier parses TeX document boundaries, balanced section commands, mathematical spans, theorem/proof/equation environments, scientific macro definitions and numbers. It reports exact sentence edits and a raw unified diff per DOI. Lean 4.28.0 mentions are toolchain metadata; the actual pin remains checked in the unchanged certificate consumer. Model assumptions, logical qualifications, changed scientific numbers or equations cannot be approved as status-only. Added non-status metadata is also held conservatively rather than silently allowed. Classifier output is implementer triage; the independent reviewer must assess the exact diff, including PDF correspondence, before approving it.

`publication_gate.evaluate_publication` will require the reviewed PUBLICATION_BINDING receipt as its exact-binding condition. This change stays in the review checkout; the already-installed production runtime is unchanged. Enforcement remains OFF. New-version bundles are local drafts outside publisher discovery and carry no DOI receipt, release binding, publication approval or independent review.

The proposed consumer source is deliberately not deployed. Do not run the existing production-hook installer from this review branch: runtime integration, approval provenance and installation packaging need a separately reviewed change. The historical runtime continues its already-approved report-only behavior.
